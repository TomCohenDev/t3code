# Machine map

Fork feature. One portal shows all T3 machines on a map. It controls what each machine can do on the other machines, and their settings. Changes apply at once on online machines and wait in a queue for offline machines. Every action in the portal is also a tool for agents.

The portal is a Cloudflare Worker with one Durable Object, at `t3.yarden-zamir.com`. Each T3 server connects to it when the server setting `machineMap` is on. The setting is off by default.

Requirements have stable numbers. Do not renumber them. Mark a removed requirement "Removed" and keep its number.

## Terms

- **Owner:** the person who signs in to the portal with an allowed email through Cloudflare Access.
- **Machine:** one T3 server (environment) that joined the map, for example Mac, VPS, Windows.
- **Device:** a browser or phone that the owner signs in with. A device is the owner, not a machine.
- **Browser key:** the DPoP key that the T3 web app keeps in one browser profile. It cannot be copied out of the browser.
- **Client:** a browser profile that the owner approved, with a name, its browser keys and its own arrows (MM-904).
- **Session:** one signed-in session of a device or an agent: a portal sign-in or a T3 session on a machine.
- **Machine token:** the Cloudflare Access service token of one machine. Cloudflare signs each request of a machine with the token's client id.
- **Arrow:** what one machine can do on another machine: a level and options. An arrow has a direction: "from can use to".
- **Level:** `none`, `read`, `standard` or `admin`. Each level maps to a fixed set of T3 auth scopes.
- **Map role:** what agents on a machine can do on the map itself: `none`, `read`, `propose` or `edit`.
- **Revision:** one numbered, saved change of the map.
- **Desired state:** the part of the map that one machine must apply: its settings, the arrows into it and the arrows out of it.
- **Command:** a one-time action on one machine, for example "restart the server".
- **Queue:** the commands and the desired state that a machine did not apply yet.

## 1. Portal and sign-in

- **MM-101** The portal runs as one Cloudflare Worker with one Durable Object that holds the whole map.
- **MM-102** Cloudflare Access protects the portal. Only the owner email opens the portal pages and the portal API.
- **MM-103** A device signs in once with Cloudflare Access. The session lasts 30 days, like the machine hostnames.
- **MM-104** Machines connect on the path `/connect` only. A separate Access app on that path accepts only machine tokens.
- **MM-105** The portal works when every machine is offline. It shows the last known state of each machine.
- **MM-106** The portal page keeps one WebSocket to the Durable Object. Every change from any source appears on every open page within one second.

## 2. Machines and enrollment

- **MM-201** "Add machine" asks for a name and a kind: laptop, desktop or server. The portal creates a machine token named `t3-machine-<name>`. It adds the token to the Access policies of the machine hostnames and of `/connect`. It also makes the tunnel of the machine (MM-213).
- **MM-202** "Add machine" shows a one-time join code. The code expires after 10 minutes and works once. The portal never shows the token secret.
- **MM-203** A machine joins with the code in one of three ways: in T3 Settings > Machines, with `t3 machine-map join <code>`, or with the agent tool `machines_join`.
- **MM-204** The join exchanges the code at `/enroll`, which a bypass Access app leaves open. The response holds the token id and secret, and the tunnel of MM-213 or null. The machine keeps the secret in its server secret store and turns on `machineMap`.
- **MM-205** A new machine shows on the map as "waiting" until its first connection. Then it shows as online.
- **MM-206** The owner can rename a machine, change its kind and icon, and move it on the map. A new name must not match the name of another machine, without regard to case. Positions are part of the map and sync to every page. A new machine takes the place that the owner picked (MM-1110), or else the free spot of the first frame of the map (1400 by 700 map pixels) farthest from the other machines. When the frame has no free spot, it goes right of every machine. The page shows cards that overlap apart, without saving it.
- **MM-207** "Rotate token" asks for confirmation and warns that the old secret stops at confirmation or after 24 hours, whichever comes first. It makes a new secret for a machine token. An online machine gets the new secret on its connection, saves it, and confirms. An offline machine has until that deadline to connect and confirm. At the deadline the portal deletes the waiting secret. Without confirmation, it keeps a recovery marker and shows "Join again with a new code" on the machine until a join code is used or the machine confirms. Making a join code supersedes a waiting rotation. A machine that needs to join again cannot rotate its token again first.
- **MM-208** "Remove machine" deletes the machine token and what MM-213 made, removes its arrows and its settings overrides, and drops its queue. A removed machine cannot connect again with its old secret.
- **MM-209** Each machine reports its tunnel hostname. Arrows out of other machines use it to connect.
- **MM-210** Without the Cloudflare API token of MM-1205, "Add machine" takes the client id and secret of an existing machine token, instead of creating one. The join code then delivers that secret.
- **MM-211** The join dialog starts with "Install and join in one step". It shows one command for Mac, one for Linux and one for Windows PowerShell, each with the code and a Copy button. Each command installs the fork and joins with the code. It links to the newest complete fork nightly (one with `SHA256SUMS`, so every installer is there) from `GET /api/fork-release`, which caches the GitHub answer for 10 minutes and falls back to the releases page, and links the `.dmg` and the `.exe`. A server install joins at once. An app install writes the code to `<T3 home>/userdata/machine-map-join-code`. The server joins with that file at its next start and deletes it first, so a bad code does not repeat.
- **MM-212** When the machine uses the code, the portal sends every page an `enrolled` event with the machine id and no part of the code. The open join dialog then plays a short sound and a one-shot pop, "joined" stamp and confetti on the code. It says "<name> joined", shows if the machine is connected, and has "Open machine". A code that expires unused shows "This code expired" with "New code". With reduced motion, the dialog keeps the state change and the sound and drops the motion.
- **MM-213** With the permissions of MM-1205, "Add machine" makes a remotely managed tunnel `t3-<slug>` with the ingress `t3-<slug>.<MACHINE_DOMAIN>` to `http://127.0.0.1:3773` and then 404. It adds a proxied CNAME to the tunnel and adds the hostname to the Access app of the machine hostnames. It reuses a tunnel with that name, or the tunnel that a CNAME with that name points at, and never makes a second one. Another DNS record with that name, or a locally managed tunnel, skips the tunnel. A failure undoes what the step made. Without a tunnel, "Add machine" works as before and the join dialog says why. The join code delivers the tunnel token, the hostname and the Access login: the team domain, the audience of the machine Access app, and the owner emails with `MACHINE_ACCESS_SUBJECTS`. "Remove machine" deletes only what "Add machine" made.

## 3. Arrows

- **MM-301** Each ordered pair of machines has one arrow. A new pair starts at level `none`.
- **MM-302** The levels map to T3 scopes:
  - `none`: no access.
  - `read`: `orchestration:read`, `filesystem:read`, `terminal:read`, `diagnostics:read`.
  - `standard`: `AuthStandardClientScopes` without `access:read`, `access:write` and `relay:write`.
  - `admin`: `AuthStandardClientScopes`.
- **MM-303** An arrow has the option "agent tools". With it on, agents on the source machine can call T3 tools on the target machine, within the scopes of the level.
- **MM-304** An arrow can expire. "For 1 hour", "for 1 day" and "until a time" set an expiry. At expiry the arrow returns to its earlier permanent level as a new revision made by the portal. A second temporary level keeps the first permanent level.
- **MM-305** The target machine enforces an arrow. A lower level ends the sessions of the source machine on the target at once, including open connections. The source then connects again with the new level, or not at all for `none`.
- **MM-306** The source machine uses an arrow. Its desktop app adds each machine it can reach, with its machine token as request headers. No pairing code is needed. When a machine refuses the connection, the app pairs again with a backoff: at least 30 seconds between two pairings of one machine, up to 10 minutes after repeated failures, and one pairing at a time.
- **MM-307** "Test" on an arrow makes the source machine connect to the target and report the result: reachable or not, the round trip time, and the scopes it got.
- **MM-308** The owner always keeps full access to every machine through Cloudflare Access. No arrow, preset or emergency pause removes it.
- **MM-309** A client has one arrow to each machine, with the levels of MM-302 and the expiry of MM-304. A new client starts at `none` on every machine. A client arrow never gives agent tools. A client arrow has no reverse, because a machine never uses a client. Machines apply the arrows of clients with an app token (MM-912), and the arrows of browser clients where `clientAccess` is `observe` or `enforce` (MM-917, MM-918). Under `off` and `observe`, an unknown browser key still reaches machines through the owner login of MM-308.

## 4. Settings

- **MM-401** The map holds shared values for T3 server settings and client settings. Each machine can override a shared value with its own value.
- **MM-402** A machine applies its settings through the T3 settings service, so they apply live like a change in T3 Settings. The theme settings of MM-408 to MM-410 and the `keybindings` setting of MM-414 are the exceptions.
- **MM-403** A desktop machine applies client settings in its desktop app. A closed app applies them at its next start.
- **MM-404** A change made on a machine in T3 Settings, to a setting with a shared value or an override, becomes an override of that machine in the map. The portal shows it as "changed on <machine>". "Make shared" copies it to all machines. A change to another setting stays local.
- **MM-405** The Settings view shows each setting as a row and each machine as a column, with a filter. Settings with a shared value come first. Values that differ from the shared value show as drift.
- **MM-406** Every setting that a machine reports is a map entry, also a setting that a later T3 version adds. A new entry has no shared value, and no machine changes. A setting syncs once it has a shared value: from the portal, from `machines_set_setting`, or from T3 Settings (MM-411). "Stop syncing" removes the shared value and the overrides. The machine-local settings (`MACHINE_LOCAL_SETTINGS` in `packages/contracts/src/machineMap.ts`: the map connection, secrets, paths, project-keyed maps, device setup) never become entries. A machine does not report or apply them, and the portal refuses a value for them.
- **MM-407** The portal edits each setting with a control for its type: a switch, a choice, a number, text, or a JSON editor for objects. The schema comes from `@t3tools/contracts`.
- **MM-408** A machine reports the themes that it publishes as the server setting `sharedThemes`. The value maps a theme id to `{ json, css }`: the content of `themes/<id>.json`, and the content of `themes/<id>.css` or null. A change in the themes folder is a local change (MM-404). The machine does not report `defaultThemeSetAt`.
- **MM-409** When a desired state changes `sharedThemes`, the machine writes each changed theme into its themes folder with atomic writes. It refuses a theme with an invalid id, a file over the size limit of the theme watcher, a symlinked theme file, or content that fails the theme file schema. Themes that are not in the value stay. A refused or extra theme shows as drift.
- **MM-410** When a desired state changes `defaultTheme`, the machine sets it like `t3 theme set`, so connected web and desktop clients switch. The value names a built-in theme or a theme that the machine publishes. An empty value clears it.
- **MM-411** A change saved in T3 Settings with "All environments" selected becomes the shared value, when the machine has the map role `edit` and a portal connection. Overrides equal to the new value go; other overrides stay. One environment sends it, about one second after the last edit. Otherwise the change stays the bulk edit of T3 Settings. A change for one selected environment follows MM-404.
- **MM-412** In T3 Settings, a server setting row shows a sync marker when the map syncs its value to the selected machine. A machine with the map off shows no marker.
- **MM-413** "Import shared values" in the Settings view takes JSON in the form `{ "server": { ... }, "client": { ... } }` and sets each key as a shared value in one revision. It refuses a machine-local key or a value that the settings schema refuses.
- **MM-414** While the server setting `keybindingSync` is on (off by default), a machine reports the rules of `keybindings.json` as the server setting `keybindings`. A change of that file is a local change (MM-404). When a desired state changes `keybindings` from the value of the previous desired state, the machine replaces the whole file and keeps the file before it as `keybindings.json.bak`. It does not write when the sync is off, when the value is not a rule list, or when the file is not a JSON array.

## 5. Commands

- **MM-501** The portal and agents can send these commands to one machine:
  - **Restart server.** The server exits, and its supervisor starts it again.
  - **Install update.** Install the waiting update now, or "when idle" with the fork rule for running agents.
  - **Stop all agents.** Interrupt every running turn on the machine.
  - **Pause scheduled tasks** and **resume scheduled tasks.**
  - **Reload windows.** Reload the desktop app windows.
  - **Start thread.** Start a thread in a chosen project with a message, like `t3_thread_launch`.
  - **Revoke client.** End one client session on the machine.
  - **Collect diagnostics.** Send a short status bundle to the portal: versions, recent errors, process list and resource use.
  - **Rotate token.** See MM-207.
- **MM-502** Each machine reports which commands it supports. The portal offers only those.
- **MM-503** Each command shows its result in the portal and in the history: who sent it, when, and the outcome.
- **MM-504** Dangerous commands ask for confirmation in the portal: restart server, stop all agents, remove machine.
- **MM-505** A server that runs as the T3 Code background service runs Install update itself. It installs the newest fork release now, or "when idle" at the first update check with no running agent turn or background shell. A server of a desktop app hands Install update to the desktop app (MM-1402).

## 6. Queue and offline machines

- **MM-601** A machine that is not connected is offline. The portal shows the time since its last connection.
- **MM-602** A change that touches an offline machine waits for it. The map shows the change at once, and marks the affected machine card or setting with a "queued" sticker and a count. A machine that never connected shows "waiting to join" instead. An arrow shows a clock and names each end that did not apply it, in plain text: "queued for <machine>" for a machine that connected before, "waiting for <machine> to join" for a machine that never connected. A "queued for" text opens the Queue of that machine, and a "waiting for" text opens the machine. The work of a machine that never connected does not count in the queued counts or the Queue tab badge.
- **MM-603** Each machine reports the last revision that it applied. Its desired state is the current map. On connection, the machine applies the current desired state, not each queued revision one by one. A revision that does not change the desired state of a machine, for example a move on the map, a note or a pair card place (MM-1108, MM-1109), queues nothing for it.
- **MM-604** An arrow with an online target and an offline source shows "applied on <target>, queued for <source>".
- **MM-605** A command for an offline machine waits in its queue. Each queued command has a delivery rule: "when online" or "when online and idle". It also has an expiry, by default 24 hours. A command that a machine took but never reported a result for expires at the same time, with that reason. A command that a machine took for its desktop app and that is not run by its expiry fails as expired; it never runs later.
- **MM-606** The owner can cancel a queued command and see why a command expired or failed.
- **MM-607** On start, a machine applies its last saved desired state before it accepts connections from other machines. If the portal is not reachable, it keeps that saved state.
- **MM-608** The Queue view lists every queued change and command of every machine, oldest first.

## 7. History, undo and presets

- **MM-701** Every change makes one revision. A revision records the number, the time, the actor, a one-line summary and the change.
- **MM-702** The actor is the owner with a device name, an agent with its machine and thread, or the portal itself for expiry.
- **MM-703** "Undo" on any revision makes a new revision that reverses it. The history keeps both.
- **MM-704** The history has a time slider. Moving it shows the map at that revision, read only. "Restore" asks for confirmation, then makes a new revision that returns the map to it, with its pair card places and notes.
- **MM-705** A preset is a named copy of all machine arrows. Client arrows are not part of it. "Save as preset" stores the current arrows. "Apply" makes one revision.
- **MM-706** Removed. The emergency pause (MM-708) replaces "Lockdown". The history still names old lockdown revisions.
- **MM-707** "Hold changes" collects changes as a draft. "Apply" makes one revision from the draft. "Discard" drops it.
- **MM-708** "Emergency pause" is a big red button under a flip-up cover. Lifting the cover is the confirmation. One press then does MM-709 and MM-710 in one step. The command palette also opens the button. An "i" button on its frame lists what one press does, from MM-709 to MM-712, with the counts of the current map: the machines that get a stop and the arrows and map roles that drop. While paused, it also shows who paused and when. It opens as a popover, and as a bottom sheet on a phone. It never moves the button. The cover, the press and Resume play short sounds. A press also flashes the page red, slams a "stopped" stamp and shakes the page once. Reduced motion keeps only the flash.
- **MM-709** Emergency pause sends "stop all agents" to every machine that joined, with delivery "when online" and an expiry of 7 days. An offline machine stops its agents when it connects again. A machine that never connected gets no stop, because it has no agents yet. The pause skips the check of MM-502: a machine without the command reports a failure.
- **MM-710** Emergency pause makes one revision with the summary "Emergency pause": every arrow, every client arrow and every map role becomes `none`. The portal keeps the arrows, client arrows and map roles from before the pause. If every arrow, client arrow and map role is `none` already, the pause makes no revision. Owner access through Cloudflare Access stays (MM-308).
- **MM-711** While paused, the portal refuses every agent tool call, `machines_read` too. It also refuses every change that raises an arrow, a client arrow or a map role, that gives a browser key to a client with access, or that sets `clientAccess` to anything but `enforce` (MM-919), from any actor. Changes that lower access, settings and commands still work.
- **MM-712** "Resume" is for the owner only and asks for confirmation. It makes one revision that returns the arrows, client arrows and map roles from before the pause, and ends the pause. It does not start agents again, and queued stop commands stay in the queue. A machine that joined during the pause keeps `none`.
- **MM-713** Every open page shows the pause at once: a hazard frame, the banner "Everything is paused" with who paused and when, and "Resume". The Durable Object stores the pause, so it survives a restart.
- **MM-714** The history groups moves in a row of one actor (machines, pair cards and notes) into one entry, for example "Moved Mac, VPS and 2 cards · 6 moves". The stop commands of one emergency pause also show as one entry. A group expands to show each revision with its own Undo.
- **MM-715** Each history entry has a colour and a sticker of one or two words by its meaning: access raised (up), access lowered (down), emergency pause and resume (hazard stripes), lockdown, settings, machines added or removed, client keys added or removed, joins and hostnames, expiries (clock), moves, notes, presets, health alerts (MM-1505) and commands that agents ran (MM-1908). A change by an agent also shows an "agent" sticker. Each entry shows the actor, the time since it happened with the exact time on hover, a short summary, and an expandable before and after of each change. Day headings separate the days.
- **MM-716** The history filters by machine, by kind, by actor and "important only". Important kinds are access raised or lowered, pause, resume, lockdown, expiries, machines added or removed and client keys added or removed.
- **MM-717** While paused, the map keeps the lines and pair cards of the arrows that the pause cut. A cut line is a red broken line. A cut pair card has a dashed red border and red stripes. Each cut row shows its level from before the pause, struck through, and a "cut" sticker. The machine panel and the arrow panel show the same. Resume restores the levels, so the lines return to normal.
- **MM-718** While paused, the desired state of every machine says `paused`. The machine saves it, so the lock survives a restart. The machine then locks T3 Code for every client except its own desktop app, which the server knows by its desktop bootstrap session. It refuses their HTTP and WebSocket auth and closes their open sockets at once. A Cloudflare Access login gets no new session while paused. Browsers get a lock screen and no data until Resume. The mobile app and desktop apps of other machines show the pause as their connection error and retry. This stops an agent that drives a browser. Agent MCP sessions follow the map rules of MM-711. A saved state that the machine cannot read locks until the next desired state.
- **MM-719** Emergency pause and Resume send the new desired state to every connected machine at once, also when they make no revision. A machine that connects later gets `paused` in its first desired state.
- **MM-720** A browser key enters a client only through an approval (MM-907), as its own change. "Undo" never adds a key back: undo of an approval into a new client removes the client, undo of an approval into an existing client removes that key, and undo of a key removal (MM-909) refuses. An owner change of a client, for example a rename from an open panel or a held draft, keeps the keys that the client has now, and so does the undo of an older client change. The undo of an old machine removal skips the arrows of clients that left the map since. "Restore" (MM-704) returns the names, places and arrows of current clients, and keeps their keys. Undo never adds, changes or removes an app token (MM-911), and refuses to remove a client that holds one.

## 8. Agents

- **MM-801** Every action in the portal is also a T3 tool on each machine:
  - `machines_read`: the map with its notes and pair card places, presence, arrows, settings, queue and history.
  - `machines_set_access`: set the level, agent tools and expiry of an arrow.
  - `machines_set_setting`: set or clear a shared value or a machine override.
  - `machines_command`: send a command, with a delivery rule and expiry.
  - `machines_queue_cancel`: cancel a queued command.
  - `machines_undo`: undo a revision.
  - `machines_preset`: save or apply a preset.
  - `machines_join`: join this machine to the map with a join code.
  - `machine_tool_call`: call a T3 tool on another machine.
  - `machine_exec`: run a shell command on another machine (MM-1908).
- **MM-802** A tool works when the machine that runs the agent has the map role for it:
  - `read`: `machines_read`.
  - `propose`: every change becomes a proposal for the owner. A proposal holds only map changes, so `machines_command` and `machines_queue_cancel` need `edit`.
  - `edit`: changes apply at once.
  - `machine_tool_call` needs an arrow with "agent tools" to the target machine.
  - `machine_exec` needs an arrow with exec to the target machine (MM-1908).
- **MM-803** An agent can never raise access for its own machine. That change always becomes a proposal, whatever the map role.
- **MM-804** Proposals wait in the Inbox of the portal. The owner approves or rejects each one. A proposal expires after 24 hours.
- **MM-805** The machine runs each agent tool through its portal connection with its own machine token. The portal checks the map role on every call.
- **MM-806** Each agent change shows in the history with the machine, the thread title and a link to the thread.
- **MM-807** Agents never approve, reject, rename, remove, invite or change the arrows of a client, not even as a proposal. Each agent write that touches a client fails. `machines_read` shows clients like the rest of the map.

## 9. Clients

- **MM-901** The Clients view lists the owner sign-ins from Cloudflare Access: device, browser, place and last use.
- **MM-902** The Clients view also lists the T3 sessions on each machine, from the machine status.
- **MM-903** The portal lists the T3 sessions of each machine with one row for each subject and label, with the number of sessions and the newest last connection. Rows with no connected session and no connection for 1 day fold away. A session without a label has its own row. "Sign out" on a row sends "revoke client" to its machine for at most 20 sessions of the row, newest first. "Sign out everywhere" ends all owner sign-ins in Cloudflare Access and all owner T3 sessions on the machines. Offline machines get it as a queued command. It keeps the sessions of approved clients (`client:<id>`): the owner removes a client to end them. It deletes the push subscriptions of every device, because a signed-out device must not get alerts; each device turns notifications on again. When Cloudflare refuses, the T3 sessions still end, and the answer says why the Access sessions did not.
- **MM-904** A client is one browser profile that the owner approved. It has a name, the Cloudflare Access email it signed in with, its browser keys and a place. It shows as its own card on the map, with a dotted line and a level sticker for each client arrow above `none` (MM-309). A new client takes the free spot of the first frame farthest from the machines and the clients, like a new machine (MM-206). The Clients view lists every client, and the command palette finds each one.
- **MM-905** A browser key belongs to one client only. The portal knows a key by its JWK thumbprint and shows it as a short code of its first 8 characters, case kept, for example `K7qP-3m_x`. A client can hold several keys, for example one per site address of a browser.
- **MM-906** A machine reports a browser key that no client holds as "seen" (MM-917), at most once a minute per key. The key then waits in the Clients view with its browser, email, machine and code, and each subscribed device gets a push message (MM-1808). Only the first reporting machine updates a waiting key, at most once a minute. One machine can report at most 5 new keys in 10 minutes, and the portal drops the rest. The portal keeps at most 20 waiting or rejected keys per reporting machine and drops the oldest. A key that stops signing in leaves after 14 days.
- **MM-907** "Approve" on a waiting key adds it to a new client or to an existing one with the same email. A new client gets the arrows that the owner picks in the same step. For the email of an existing client, the form starts with the permanent arrows of the newest such client. For any other email, it starts at `none`. A key that joins an existing client gets the arrows of that client, and the approval refuses arrows. While paused, the approval refuses a key for a client whose arrows the pause cut, because Resume would give the key access without the check of MM-711. Approve runs on the approval path of MM-1207.
- **MM-908** "Reject" keeps the key in the list as rejected. It gets nothing, and its new reports only refresh the time. "Unblock" returns it to waiting.
- **MM-909** The client panel sets the level of the client on each machine, with an expiry, renames the client, and removes one of its keys. A removed key can sign in again and wait. Machines end the sessions of a client that lost a key (MM-917), and its other keys sign in again.
- **MM-910** "Remove client" removes the client with its keys and arrows.
- **MM-911** A client can hold one app token: a Cloudflare Access service token for a native app, for example the T3 Android app. The portal adds it to the policy `t3 client tokens` of the machine hostnames app, never to the `/connect` app, so an app token cannot connect as a machine. The portal stores its client id and never its secret. Only the portal sets or replaces an app token.
- **MM-912** The desired state of a machine lists each client with an app token and an arrow to that machine above `none`. The machine gives a request signed with that token a session with subject `client:<id>` and the scopes of the level (MM-302). It refuses new sessions after an expiry itself, and ends the open sessions of that client at the expiry, also while the portal is unreachable (MM-1306). When the level changes or the client leaves the list, the machine ends those sessions, open connections too, like MM-305. The pause (MM-718) locks them, and turning the map off or leaving it ends them. A client token is never an owner subject, so without an arrow it gets nothing.
- **MM-913** "Invite an app" makes an invite for a new client, with a name and arrows, or for an existing client, which keeps its arrows. It runs on the approval path of MM-1207. Only the owner makes an invite, in the portal. No agent tool and no T3 client path makes or cancels one. The invite is a QR code and a link, `https://<portal>/enroll/client#code=<code>`, with a 128-bit code that works once and expires after 15 minutes. A new invite ends the older invites of the client. The client panel shows a waiting invite with "Cancel invite", and the invite dialog has the same button; the code then stops working. The app sends `POST /enroll/client` with the code and its device; the Bypass Access app of `/enroll` (MM-204) covers that path. Only then does the portal make the app token, so the secret is only in that answer, with the client id, the machines of MM-914 and the URL of MM-914. ## 12. Security

- **MM-1201** The Durable Object stores no token secret at rest. During a join (MM-204) and a rotation (MM-207), it keeps the secret and the tunnel token (MM-213) encrypted with a Worker secret. It deletes the secret when the machine takes it, or when the code or rotation expires.
- **MM-1202** A machine gets only its own desired state, its own queue and the public facts of other machines: name, kind, hostname, presence and the arrows that touch it.
- **MM-1203** Every write records its actor. The portal refuses writes from a machine without the map role for them.
- **MM-1204** `/enroll` limits attempts per address and refuses expired or used codes.
- **MM-1205** The Worker keeps one Cloudflare API token as a secret. The token can only edit Access service tokens, Access apps, Cloudflare Tunnels of the account, and DNS of the zone of the machine hostnames, read and edit the Zero Trust organization, and revoke Access sessions of the organization. Without the tunnel and DNS permissions, MM-213 skips the tunnel. Without the organization read permission, approvals (MM-1207) stay off. Without the organization edit permission, "Set up approvals" (MM-1208) shows the manual MFA step. Without the revoke permission, "Sign out everywhere" (MM-903) ends only T3 sessions, and the approvals check (MM-1208) names the missing permission.
- **MM-1206** A machine trusts the Cloudflare Access JWT header only because its T3 server listens on loopback behind its tunnel, as the fork login already requires.
- **MM-1207** Approving a browser key needs a fresh MFA. Approve runs only on `/api/grant/*`, which has its own Access app. That app lets in only the owner emails and asks for a passkey or a security key through Cloudflare independent MFA. Its app session and its MFA session last 10 minutes. The Worker accepts its JWT for 10 minutes after Access issued it. Before each approval, the portal reads the app and the Zero Trust organization from Cloudflare and refuses when any of these settings changed or when the organization allows no passkey or security key. So a stolen portal login cannot approve its own browser. The passkey check is a Cloudflare page, not a browser prompt. Next to "Confirm with passkey", the portal says that Cloudflare opens a page for the passkey and then returns. It links the enrollment page `https://<TEAM_DOMAIN>/AddMfaDevice` for an owner without a passkey. Known limit: an identity provider whose MFA Access matches by AMR skips the prompt. Revisit if the owner login moves to such a provider.
  Invites, browser-key approvals and owner-only changes, including a held draft, share one saved-request flow. Before leaving for Cloudflare, the page keeps the exact request in tab storage with a 10-minute expiry, never an invite code or secret. A successful return consumes it and runs it once. Before it runs, both the page and the server check the affected items against the saved state. A changed or removed item shows "This changed while you confirmed. Review and try again" without applying the request. A failed or interrupted check, an expired request or missing saved data shows a clear message and "Try again". Retry starts a fresh confirmation when the affected state still matches; otherwise the owner reviews the current item and request first. Unrelated map changes and a waiting key's last-use refresh do not invalidate the request.
- **MM-1208** "Set up approvals" in the portal creates the approval Access app of MM-1207 with the Cloudflare API token, or makes it again when someone changed it. It also creates the Access app of `/client` (MM-914) once. A portal without the `/client` app reports it as a setup problem, so "Set up approvals" shows again. When approvals are ready, the check also warns when the token cannot revoke Access sessions (MM-1205), at most once an hour. The warning does not stop approvals. Before it creates an app, "Set up approvals" allows the passkey and the security key in the Zero Trust organization when the organization allows neither. It keeps every other organization setting, and it does not turn on MFA for all apps. It also creates the App Launcher app for the owner emails when the account has none, because passkey enrollment needs it. It changes neither when it is present. Cloudflare error 12130 on the approval app shows the manual MFA step of MM-1209.
- **MM-1209** When the portal does a Cloudflare step itself and the API token lacks the permission for it, the portal explains the manual step instead. The explanation gives the Zero Trust dashboard path, links to the dashboard and the Cloudflare docs, and the name of the missing permission. It never shows the raw Cloudflare API error for a missing permission. A long error text wraps inside its box. Known gap: the tunnel setup of MM-213 still shows the API error with the permission names (fork issue #230). Revisit at the next change of MM-213.

## 13. T3 server

- **MM-1301** The server setting `machineMap` holds `enabled` and the portal URL. It is off by default. Off means no connection, no change to auth, and no joined tunnel (MM-1309).
- **MM-1302** The machine token secret lives in the server secret store, never in `settings.json`.
- **MM-1303** The server keeps one outbound WebSocket to `/connect`, with backoff after a failure.
- **MM-1304** The server saves the last desired state in its user data, so MM-607 works after a restart.
- **MM-1305** For a request with a valid Cloudflare Access JWT of a machine token, the server looks up the arrow from that machine. It issues the session with the scopes of the level and the subject `machine:<id>`. Level `none` refuses the request. When the same subject, method and label ask again, the server gives the same session again if it has the same scopes, more than half of its life left, and was seen within 7 days. Else it issues a new one and ends the other sessions of that identity that are not connected. This also applies to the `client:<id>` sessions of app tokens (MM-912). Owner sign-ins through Cloudflare Access and browser clients (MM-917) always get a new session, because one label covers every browser of the owner or of a client. Two requests at once get one session. The server ends `machine:<id>` and `client:<id>` sessions and owner Access sign-ins when they are not connected and were not seen for 7 days. "Seen" is the later of the issue and the last connection start. The first sweep runs one hour after start, so that clients can connect again after a restart, and then every hour. Each sweep, and each new session of an identity, ends at most 500 sessions, oldest first, so that a large backlog ends over several hours without a flood of updates to clients.
- **MM-1306** When the level of an arrow into the server changes, the server revokes every session with the subject of the source machine. The server compares the level that the sessions got, read at the time the old desired state arrived, with the level now, so an arrow that expired in between counts as a change. At the expiry of an arrow into it, the server also revokes those sessions itself, without waiting for the portal revision, and so does a server that restarts after an expiry. The server saves the subjects to revoke with the desired state, and a revocation that fails runs again until it works.
- **MM-1307** The server accepts T3 tool calls from a machine session only when its arrow has "agent tools".
- **MM-1308** Fork code lives in new files. Changes to upstream files are small hooks. A hook has a test only when it could break without a visible error.
- **MM-1309** A join with a tunnel (MM-213) saves the tunnel token in the server secret store and the hostname and Access login in `<stateDir>/machine-map-tunnel.json`. The server then restarts through its supervisor. At start, the server uses that tunnel as its tunnel URL and Access login. It installs the pinned `cloudflared` of the relay client, with its sha256 checked, runs it as a child process with the token in its environment, starts it again after each exit, and stops it with the server. The tunnel applies only while the map is on: turning the map off stops `cloudflared`, and the next start does not use the tunnel. "Leave" stops `cloudflared` and forgets the tunnel.
- **MM-1310** A tunnel URL or Access login from the environment or the desktop settings wins over the tunnel of a join. Then the join keeps the tunnel of the server and starts no `cloudflared`.
- **MM-1311** While the map is on, the server trusts the origin `https://<hostname>` of each peer in its desired state like a trusted browser origin: credentialed CORS, cookie sessions, and the `trustedBrowserOrigins` that clients read. Explicit trusted origins stay in addition.

## 15. Resources and health

- **MM-1501** While connected, a machine sends a resource sample on connection, every minute, and when the portal asks. The portal asks at most every 10 seconds per machine. A sample holds: CPU percent, CPU work without nice time, steal, CPU pressure (MM-1509) and load averages, memory, swap and swap traffic, disk of the T3 home volume, network rates, the T3 server process, the processes that T3 started (count, CPU, memory), the top 5 processes by CPU and by memory, and the battery (MM-1510). A value that the platform does not give is null. Sampling reuses the T3 resource telemetry and runs at most five short commands per sample.
- **MM-1502** The sample messages stay outside the base protocol unions. An older portal ignores a sample, and the portal works with a machine that never sends one.
- **MM-1503** The portal keeps one point per machine and minute for 24 hours, and one point per hour (the average, with the CPU peak) for 30 days, in SQLite. Each machine has a size cap. The portal refuses a sample message over 8 KB. The alarm prunes old points every hour. The portal clock places each point.
- **MM-1504** Each machine has health thresholds. The defaults are: CPU starved (MM-1509) for 30 minutes, with CPU pressure above 20%, or without pressure CPU work above 95%, memory above 90%, disk above 90%, swap traffic above 10 MB per second for 5 minutes, offline for more than 15 minutes, and battery below 15% while discharging (MM-1511). The owner edits them per machine in the machine panel. An empty field turns a check off. Thresholds are portal data, not T3 settings and not map revisions.
- **MM-1505** An alert starts when its threshold is crossed and ends when it is not. The machine card shows one sticker per active alert: HOT (CPU), FULL (memory), DISK, SWAP, DOWN (offline), LOW (battery). Alert starts and ends show in the History view as portal events, not as map revisions. Ended alerts stay 30 days, at most 500.
- **MM-1506** The machine card shows CPU and memory bars, and a battery bar under MM-1510. The machine panel shows charts of CPU, "Waits for CPU" (CPU pressure, where the machine reports it), memory, battery (under MM-1510), disk and agent processes for the last hour, 24 hours and 30 days, the CPU signals in plain words, the top processes now, the thresholds, and a link to the "Collect diagnostics" command. The Health view compares all machines side by side, with the CPU waits and steal where the machine reports them, and lists the alerts with their start time. Bars and charts change only when a sample arrives.
- **MM-1507** `machines_read` returns the latest sample, the thresholds and the active alerts of each machine. `machines_resources` with a machine id and a range (`hour`, `day` or `month`) returns the history and the alerts of that machine. Both are read only and need the map role `read`.
- **MM-1508** Charts are SVG polylines from a small helper in the portal. A missing step breaks the line instead of drawing a guess.
- **MM-1509** The CPU check means "the machine is starved", not "the machine is busy". On Linux the signal is CPU pressure: `some avg300` of the `cpu.pressure` file of the cgroup of the T3 server, which holds its agents, or of `/proc/pressure/cpu` when that cgroup has no file. On macOS, Windows and Linux without pressure files, the signal is CPU work without nice time, idle, I/O wait and steal, since the previous sample. So low priority work, for example a deploy build with Nice=10, does not start the alert. A sample of an older server has no new CPU values; its CPU check stays off until it updates.
- **MM-1510** A machine with a battery reports it in its sample: the percent, the state (charging, discharging, full, or on power and not charging), and the minutes left when the system gives them. macOS reads `pmset -g batt`. Linux reads the first `/sys/class/power_supply/BAT*`: `capacity`, `status`, and energy or charge with power or current for the time left. Windows and a machine without a battery report none. The field is optional: a sample of an older machine has no battery. The portal shows the battery only while it charges or discharges and is below 100%. It hides a full battery, and a battery on power that does not charge, for example at a charge limit of 80%. It shows on the machine card, in the Health view with the time left in words, as a chart in the machine panel, and in its facts.
- **MM-1511** The battery alert starts while a machine runs on its battery below the battery threshold, by default 15%. The owner changes the threshold per machine, and an empty field turns the alert off. A low battery on power is no alert.

## 16. Scheduled tasks

- **MM-1601** Each machine reports its scheduled tasks in its status: id, title, on or paused, the schedule in words, the next run, the last run and the last result.
- **MM-1602** The Tasks view lists the tasks of every machine, grouped by machine. Each task has Pause or Resume and "Run now". They are the commands `setScheduledTaskEnabled` and `runScheduledTask`, so an offline machine gets them from its queue. The machine panel links to the tasks of its machine.
- **MM-1603** Each task row shows the title, the schedule in words, an "on" or "paused" sticker, the next run, the last run and the last result. A failed run shows its error text.
- **MM-1604** The portal offers Pause, Resume and "Run now" only when the machine reports the command (MM-502). A machine without tasks in its status shows "This machine does not report its tasks yet. Update T3 on it."
- **MM-1605** "Tasks N scheduled" in the Overview of the machine panel opens the Tasks view with only that machine. "Show all machines" ends the filter.

## 17. Machines panel in T3 Code

- **MM-1701** T3 Code has a Machines panel, opened like the pull requests panel. It shows the machine map natively from the data of `machines_read`: the machines, their presence and work, the arrows, the queue and the tasks. It works in the web and desktop clients. It is read only and links to the portal. Without a portal connection or while paused, it says why it has no map.

## 18. Installed app

- **MM-1801** The portal is an installable web app on desktop Chrome and Edge, on Android and on iOS Safari. The manifest has an id, a scope, the `standalone` display, a maskable icon and the shortcuts of MM-1806. The page registers the service worker `/sw.js` for the whole portal.
- **MM-1802** The service worker caches only the files of the current build and the offline page. Each build makes a new worker, which drops the files of older builds. It never caches the page HTML, API answers or socket data, so the portal never shows old machine state.
- **MM-1803** A page load always goes to the network. Only when the network fails, the worker shows the offline page: "Offline. The portal needs the network."
- **MM-1804** The worker passes the Cloudflare Access redirect of a page load to the browser unchanged. When the Access session ends, the open page shows "Your sign-in ended" with "Sign in again" and stops reconnecting. "Sign in again" loads the page again, so Access signs in and returns to the portal.
- **MM-1805** The app icon shows a badge with the count of Inbox proposals, sign-ins that wait for approval (MM-906) and active health alerts, where the browser has the Badging API. Each push message (MM-1807) holds the count, so the badge stays current while the app is closed.
- **MM-1806** The app shortcuts are "Emergency pause", which opens the big red button (MM-708), Inbox, Health, Queue and Tasks. Each shortcut has its own maskable PNG icon in 96 and 192 pixels, because Android ignores SVG shortcut icons. A shortcut or a notification opens in the open portal window when there is one.
- **MM-1807** The portal sends Web Push with the Web Crypto API of Workers and no push library. It signs with the Worker secret `VAPID_JWK`. Without the secret, push is off. Each device has its own subscription, stored in the Durable Object with its sign-in. The portal deletes a subscription that the push service reports as gone.
- **MM-1808** The portal sends a push when a health alert starts (MM-1505), when a new proposal waits in the Inbox, when a new sign-in waits for approval (MM-906), and on the emergency pause. The pause push skips the device that pressed the button. The DOWN alert is the push for a machine that went offline, after the offline threshold of MM-1504. Alert ends and Resume send no push. A tap on a notification opens its view.
- **MM-1809** The Clients view has "Notifications on this device" with "Turn on", "Turn off" and "Send a test". On iOS, push works only in the app on the Home Screen, and the section says so in Safari. A blocked permission and a missing `VAPID_JWK` show why push is off. A new VAPID key turns the old subscription of the device off.

## 19. Cross-machine work

- **MM-1901** The arrow from A to B is the only machine-to-machine grant. Each cross-machine feature uses B's T3 server. It uses neither SSH nor a shared database.
- **MM-1902** Each cross-machine call stays within the source thread's runtime mode, interaction mode and tool capabilities, and the arrow's grant. The narrower limit wins. A thread read of MM-1905 works in every mode: A pairs that session without `orchestration:operate`, B makes such a session read-only, and B refuses every write on it.
- **MM-1903** A machine's map role never raises a thread's limits. A restricted thread cannot use `edit` to change settings, send commands or raise access.
- **MM-1904** When B cannot enforce a source limit, A refuses the call before it sends work. A checks the live caller again after pairing, after the MCP handshake and before a retry. B never lends its map role or onward arrows to the caller.
- **MM-1905** One server-side thread reader serves `t3_thread_read` and thread attachments. It reads local threads from the local database and other threads through the same arrow and checks as `machine_tool_call`.
- **MM-1906** A thread attachment keeps its `environmentId`. The composer send check waits for the list of readable machines, then accepts a reachable thread on another machine and reports a refused or unavailable read without sending incomplete context.
- **MM-1907** The `@` thread menu on web, desktop and mobile lists reachable threads across machines. When more than one machine is reachable, each item names its machine. Thread chips and message links still open the correct thread and message.
- **MM-1908** An arrow has an explicit `exec` capability, off by default. It works only with agent tools and the level `standard` or `admin`. Turning agent tools off turns exec off. The arrow panel toggles it, and Map, Table and the arrow panel show an "exec" sticker. `machine_exec` runs a command through B's T3 server, as B's T3 user, in B's home directory or a given directory, for at most 90 seconds. It returns the exit code, stdout and stderr. Each stream keeps at most 50,000 bytes and then ends with a truncation marker. B reports each run to the portal. History and `machines_read` show the source machine, the calling thread, the command, the working directory, the outcome, the exit code and the time, never the output.
- **MM-1909** The arrow and the caller's credentials control command execution. No shell command blocklist or command-pattern block grants or refuses execution.
- **MM-1910** `delegate_task` accepts a target machine. The child runs on B. `task_status` and `task_cancel` reach that child through the arrow. Completion wakes the parent on A.
- **MM-1911** `orchestrator_capabilities` lists the providers and models of reachable machines with their machine and environment ids. A delegation stores both ids with the parent and child thread ids, so a later cross-machine parent link needs no local-only thread reference.
- **MM-1912** Watches use one server-owned record with a watcher kind, a target, a wake rule, a change cursor and the parent machine, environment and thread ids. `watch_pull_request` uses a pull-request kind. CI runs, threads and tasks can add kinds without a separate wake system.
- **MM-1913** A watch and its pending wakes survive a server restart and a disconnected machine. Each wake has a stable id; the parent's server records it once and acknowledges it, so a retry cannot wake the parent twice. Cancel stops later wakes; status shows waiting, delivered, cancelled or refused.
- **MM-1914** Cross-machine watch reads, cancellation and wake delivery use the arrow and the source limits. A removed grant stops work and delivery; restoring it rechecks permission before resuming.
- **MM-1915** Each arrow shows an explicit capability list: read threads, launch or delegate, exec, copy secrets, and settings. The portal reads it as "what can A do on B", also on a phone.
- **MM-1916** Arrow removal and emergency pause stop every cross-machine capability, including queued work and watch delivery. Resume does not restart cancelled work.
- **MM-1917** The service that copies `.env` files or secrets to another machine, including "add project to another machine", needs the arrow's copy-secrets capability. Neither launch permission nor `exec` alone permits that service.
- **MM-1918** Each cross-machine UI feature works on web, desktop and mobile, through local, remote, relay and tunnel connections. UI, MCP tools and scheduled work call the same server services and checks. Unsupported provider operations report that limit without using broader credentials.
